| S-07 | Medium     | CSRF / cookie auth           | Mitigated (draft)  | API uses bearer session credentials, not cookie session for `/api/v0`. HTML `/app` uses a `Secure`, `HttpOnly` cookie scoped to `/app`: `SameSite=Strict` while `SUAS_CORS_ALLOWED_ORIGINS` is empty, `SameSite=None` only when it is non-empty. Every browser-originated unsafe request is checked before body parsing, authentication, rate limiting, and email: same-origin (`Sec-Fetch-Site`, including `Origin: null`) or an origin in `SUAS_CORS_ALLOWED_ORIGINS`, otherwise `403` (`src/http/origin-policy.ts`; verified in a real Chromium session). A cookie-authenticated unsafe request with neither `Sec-Fetch-Site` nor `Origin` is `403`. Every allowlisted origin gets full `/app` session read and write, so only owner-controlled origins may be listed. A build pinned below spec 0.7.0 rejects a non-empty allowlist at startup in every environment, `SUAS_ENV=TEST` included, so none of this is active until D-038 is released and the pin is bumped. Accepted limits: Safari blocks and Firefox partitions third-party cookies, so a cross-site frontend should use Bearer; browsers that send no `Sec-Fetch-Site` fall back to the `Origin` rule (scheme and host). Proposed D-038, draft: supersedes the 0.6.0 cross-origin rejection rule pending a released spec amendment. |
