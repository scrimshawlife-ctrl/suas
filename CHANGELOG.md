# Changelog

All notable changes to the SUAS Worker (web `/app` and `/api/v0`) are recorded
here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the project uses [Semantic Versioning](https://semver.org/) while it stays
pre-1.0. The application version lives in `package.json` and is reported as
`app_version` by `GET /api/v0/admin/build-info`.

The application version is not the specification stack version. Each release
below states which SUAS-specs stack it implements (SUAS-specs `VERSIONING.md`
section 3). Versions below 1.0.0 mean no production, pilot, or app-store launch:
SPEC-018 is still blocked. Release steps: [RELEASING.md](RELEASING.md).

## [Unreleased]

### Changed

- **VA Veteran Confirmation is the request gate** (suas-specs #72 R9.1; the owner accepted the direction on 2026-11-11, the spec is not released yet; D035_VA_CONFIRMATION_ADAPTER.md §4–§15). Requesting help, Resources, Check-Ins, Trusted Contacts and Consent Grants now need a `VERIFIED` standing: a VA confirmation, a manual review or a D-016 self-attestation, with a `REVOKED` row outranking all three; helping, Serve, chat as the accepter and the crisis screen stay open. New `POST /api/v0/veterans/me/verification/va/confirm` (signed in, `Idempotency-Key` required) takes the `VA_CONFIRMATION_V1_REQUIRED_ONLY` projection (first and last name, birth date, street, city, state, `USA`, ZIP; no SSN) plus `noticeVersion: "va-notice-v1"` (`400 VA_NOTICE_VERSION_REQUIRED` otherwise), sends the projection once and returns `{ status, not_confirmed_reason, verified_at, failure_class }`. The typed name must match the account display name (`409 VA_NAME_MISMATCH`, no VA call); one VA-verified identity per tenant (`409 VA_IDENTITY_ALREADY_VERIFIED`, checked only after VA verifies, generic message, counted), keyed on the canonical form of VA_CONFIRMATION_FLOW §2.2: first and last name joined as one string (so a name split differently between the fields is the same identity), lower-cased, NFKD, marks stripped, letters NFKD keeps whole folded (ß→ss, æ→ae, œ→oe, ø→o, ł→l, đ/ð→d, þ→th, ı→i, ŋ→n), then a–z only, `|`, ISO birth date. A VA 400 is `UNAVAILABLE` / `REQUEST_INVALID` and 404 or any unclear answer `UNAVAILABLE`, never `NOT_CONFIRMED`; the adapter reads at most 64 KiB of response. At most 5 VA-answered attempts per person in the last 24 hours (`429 VERIFICATION_ATTEMPT_LIMIT` with `Retry-After`); outages and VA 400s (`UNAVAILABLE`) never count. A backstop cap of 20 VA calls per 24 hours counts the same rows (owner, suas #238, 2026-11-12; same 429, its own message). A VA `VERIFIED` standing answers without a VA call. Each attempt is written `PENDING`, VA is called with no database lock held, then the attempt settles; the attempt row is its own idempotency record (24 h). Projection values are never stored, logged or put in events: the row keeps the result, the notice version, an HMAC request fingerprint and, for answers VA gave, an HMAC identity hash, each with its key id, under the new secret `SUAS_FINGERPRINT_KEY` (base64, at least 32 bytes, not the session secret) and `SUAS_FINGERPRINT_KEY_ID`; optional `SUAS_FINGERPRINT_KEY_PREVIOUS` / `_PREVIOUS_ID` are verify-only during a rotation, and a retry after a rotation is a new attempt, never a 409. Startup fails when VA confirmation is on without the key. New `POST /api/v0/veterans/me/verification/commands/self-attest` (signed in, `Idempotency-Key`, empty body) writes a `SELF_ATTESTATION` `VERIFIED` row with no VA call or limit, whatever the VA mode; `403 VERIFICATION_REVOKED` when revoked. `GET /veterans/me` `id_verification` becomes `{ method, status, not_confirmed_reason, verified_at, failure_class }` with method `VA_VETERAN_STATUS`, `MANUAL_REVIEW` or `SELF_ATTESTATION`. `GET /veterans/me/id-verification` and `POST /veterans/me/id-verification/commands/start` are removed. New `SUAS_VA_CONFIRMATION_MODE` (`disabled` default, `fixture` LOCAL/TEST only, `sandbox` STAGING/LOCAL only), `SUAS_VA_CONFIRMATION_BASE_URL` (sandbox URL only), `SUAS_VA_CONFIRMATION_API_KEY` (secret) and `SUAS_VA_CONFIRMATION_PROJECTION_ID`. The fixture fails closed: an unlisted ZIP is `NOT_CONFIRMED` `PERSON_NOT_FOUND`. Migrations `0022_va_veteran_confirmation.sql` and `0023_va_confirmation_review_fixes.sql` (schema version 23; 0022 is unchanged from #236, so a database that applied it moves forward); a revocation or account deletion frees the verified identity, including one written while a VA call is in flight, and deleting an account also clears the identity hash from its other VA rows (`NOT_CONFIRMED` included). `sandbox` mode refuses to start unless the SHA-256 of the vendored projection file (`contract/va-projection/`, copied byte for byte from suas-specs `evidence/d035/` and embedded by `npm run va:projection`) equals `projection_sha256` in its approval record and that record is `APPROVED` (VA_CONFIRMATION_FLOW §3, A27; D035 §7). The record is `DECISION_PENDING` today, so `sandbox` does not start until the Privacy Owner approves; `fixture` and `disabled` need neither. `npm run va:sandbox-smoke` runs one manual sandbox call. A VA "not confirmed" answer with a missing or unknown reason is now `UNAVAILABLE`, not `NOT_CONFIRMED`.
- **Web Verify page: a VA check or self-attestation** (suas-specs #72 R9.1, proposal). `/verify` drops the ID scan and selfie stepper. It shows the versioned notice `va-notice-v1` before a form (name, date of birth, current address or where you get mail) sent to `POST /veterans/me/verification/va/confirm` with `noticeVersion`, and offers "Tell us you served" (`POST /veterans/me/verification/commands/self-attest`, the D-016 fallback) beside it and on every view except revoked. Field-level checks mirror VA's patterns. One `Idempotency-Key` per distinct body; a `409 IDEMPOTENCY_CONFLICT` drops it so the next send is new. Each answer has its own view: confirmed, self-attested, not matched, not confirmed, VA refused the request (correctable), VA unavailable, VA check off (503), the VA check limit in the last 24 hours (5 answered tries or 20 calls), name mismatch, details that can't be used for this account, and revoked; every view but a confirmation links to Serve and the crisis screen. Raw codes are never shown, and the details are not kept in storage, the address bar or the query cache. Continue with no return path goes to `/request`. Landing and `/verify` say "confirm with VA or tell us you served".

- **Spec pin 0.9.0.** `src/release/pins.ts` now pins SUAS-specs `0.9.0` (`RELEASE_MANIFEST-0.9.0.md`, tag `v0.9.0`, specs commit `208705c`), up from `0.7.0`. CI, deploy and staging workflows, `wrangler.jsonc`, `.env.example` and the test environment carry the same two values. The `/api/v0` selector and event schema `0.1.0` are unchanged. Readiness stays `NOT_READY`; SPEC-018 stays blocked.

A missing image settles `PHOTOS_GONE`; open reviews older than 29 days settle `PHOTOS_EXPIRED`. Only reader-answered submissions count (3, and a cap of 10, per rolling 24 hours). - **API for the v1 web app** (local v1 plan; not a released spec). Self sign-up: `POST /auth/challenges` still answers `202` for any address, and an unknown email now also gets an `EMAIL_OTP` code when `SUAS_BROWSER_TENANT_ID` is set; verifying it creates an `ACTIVE` user in that tenant (never a tenant chosen by the request). A challenge verified by a `SUSPENDED` or `REVOKED` user gets no session. Migration `0016_display_name.sql` adds `users.display_name` (trimmed, 1 to 40 characters); `PUT /veterans/me/profile` sets it and `GET /veterans/me` returns `display_name` and `is_admin`. New `GET /chat/threads`. `PATCH` is now an allowed CORS method. ### Fixed

- **Check-In answers and completion (A2-02, A2-10, A5-02, A5-03, A2-25, A2-28; CHECKINS.md §4.2, §4.4, §6; SIGNAL_SCORING.md B1).** `POST /check-ins/{id}/responses` refuses a `question_id` outside the Check-In's questionnaire version, or an `answer_option_id` that is not one of that question's options, with 400 `VALIDATION_FAILED` (it was 500 for an unknown id and silently accepted a wrong option, so scoring later failed and a RED answer produced no signal). A completion replay enqueues `support-signal.compute` again under the same `support-signal:<id>` key, so a lost enqueue is recovered on retry; new `requeueUnsettledCheckIns` finds completed Check-Ins with no settled signal and no compute job and enqueues them (CHECKINS.md §6 rules 6-7). `POST /check-ins` returns the in-flight Check-In (200) instead of starting a second one. Check-In responses carry `started_at`.
- **Idempotency reservations expire (A2-07, A2-20; API.md §7 rule 5).** A `RESERVED` command record left by a request that crashed or timed out no longer blocks its key forever: after a 120-second lease an identical retry runs the command again (the API Lambda times out at 30 seconds). The unreachable `FAILED_FINAL` path (`isFinalFailure`, `CommandFailedFinalError`) is removed; a failed command is always retryable.
- **Case and contact commands commit with their idempotency record (A2-06, A2-08; API.md §7 rules 2, 3, 5; EVENT_MODEL.md §2.1).** `POST /cases/{id}/commands/{activate,move-to-followup,resume-active,escalate,close,triage,reopen}`, `log-contact-attempt` and `complete-contact` now run in the transaction that records the command result, so a retry after a lost response replays the original result instead of a 409. The contact event's dedupe key is scoped to the case, the caller and the command, so a reused `Idempotency-Key` on another case records that case's contact instead of returning the first case's. A Domain Event key that already belongs to another aggregate is refused with 409 `IDEMPOTENCY_CONFLICT`.
- **Admin case commands need MFA (ADMIN.md §2, SECURITY.md §2).** `POST /cases/{id}/commands/triage`, `/reopen`, and `/close` acting as a SUAS System Administrator now answer 403 `MFA_REQUIRED` unless the session is MFA-elevated, like every other admin route. A helper's own `close` is unchanged.
- **Web Check-In and chat (QA sweep SUPPORT-1, SUPPORT-4, SERVE-6).** Home's Check-In card no longer promises "Four short questions" (the Check-In has nine). A Check-In the server refuses to continue (past its window, or finished elsewhere) shows "This Check-In can no longer be finished" in a focused heading with Start again, instead of "Check your connection". Chat sends one message at a time per conversation, so messages are stored in the order typed; a send with no answer after 30 seconds shows "Not sent." and the next message still goes. "Try again" after a failed Check-In start starts one Check-In on a double click.
- **Web double clicks send once (QA sweep REQUEST-1, SERVE-3, SUPPORT-3, SUPPORT-9, SUPPORT-10, ADMIN-1, ADMIN-5).** Buttons were disabled only by TanStack Query's `isPending`, which flips after the next render, so a fast double click sent the command twice; the second got `409 IDEMPOTENCY_CONFLICT` and the page showed a false failure although the action worked. A small `useSingleFlight` guard (`web/src/lib/single-flight.ts`) now drops a second call while the first runs, on the requester's Confirm and Cancel, the helper's case commands, contact log and Take, Check-In Save and Skip, the RED-notice switch, Stop sharing and Remove, MFA Start check and Confirm, draft Publish, Discard and Save, and the sign-in, request, edit, intake and trusted-contact forms.
- **Web not-found pages and stale re-reads (QA sweep REQUEST-2, SERVE-2, ADMIN-4, SERVE-4).** A malformed id in `/requests/:id`, `/serve/requests/:id` or `/admin/drafts/:id` (the API's `400`) now reads as not found instead of a connection problem with a Try again that cannot help. The request detail read no longer retries a `4xx`, so a case that is not yours says so at once instead of after about 7 seconds. The "a 4xx is final, a 5xx gets two more tries" query rule now lives once in `web/src/api/errors.ts`. A helper who releases a request no longer re-reads it on the way out (a console 404).
- **Web sign-out, session expiry, MFA focus and links (QA sweep AUTH-1, ADMIN-8, ADMIN-2, SERVE-1, SERVE-5, REQUEST-3).** A 401 counts as an expired session only when the request carried the token still in use, so signing out while a page loads ends on the landing page, and two 401s from one expiry keep the first return path. An empty MFA response moves focus to the field. Notifications' "Back to home" returns to Serve in Serve mode. Requester-only notices (released, expired) link to `/requests/:id`. An unverified helper who accepted a request reaches their case from `/requests/:id`; everyone else unverified still goes to `/verify`. Client only; no API or auth rule changed.

Migration `0018_current_case_index.sql` narrows the one-current-case-per-Veteran index to cases that are not RESOLVED or CLOSED, so a RESOLVED case and a new case can coexist. `openCase` and every reader of "the Veteran's case" (`me.open_case`, signals, check-ins, legacy `/app`) skip RESOLVED cases; the old case stays intact. Migration `0017_request_holder.sql` adds `service_requests.accepted_by_user_id` (backfilled from chat threads and case assignments). `EXPECTED_SCHEMA_VERSION` moved to 17 with that migration and to 18 with `0018_current_case_index.sql`. A helper could never START or FULFILL, and the requester never saw `RESPONDER_ACCEPTED`. The accepter is a peer, not an outside provider, so no provider consent is evaluated; `ASSIGN` and its consent guard are unchanged. Requests that are no longer waiting (cancelled, past matching, already accepted) are still refused. Next legal commands: accepter START then FULFILL, requester CONFIRM. Every sign-in challenge branch (enrolled, new, suspended, unknown) now writes one challenge row and one audit event, and a failed send is audited and still answers `202`. Request summaries are returned only when they are a string, cut to 280 characters. `POST /cases/{caseId}/service-requests` accepts only `summary`, `timing` and `meeting_place` in `details`, with the same bounds as the plain form (other keys are `400`). Resolve counts a requester confirmation only from the current resolution cycle, read inside the resolve transaction, and stores its time. `SUAS_BROWSER_TENANT_ID` must be a UUID whenever it is set.
- **Requester-only commands.** The accepter could run CONFIRM and CANCEL, and SUBMIT on a request they created. SUBMIT, CANCEL and CONFIRM are now the requester's alone (`403` for anyone else); the accepter runs every other command. - **Resolve takes its actors from the server.** `authored_by`, `accepted_by_user_id` and `veteran_confirmed_by` were read from the request body. They are now the session user, the case's active assignment, and the requester when a request on the case was confirmed; body values are ignored.
- **Accept order.** An ineligible caller (other county, not widened) got `409 ALREADY_CLAIMED` for a request someone else had accepted, which revealed it existed. Visibility is now checked first: ineligible callers get `404`, only eligible losers get `409`.
- **Job outbox.** `job-worker` had no handler for `notification.send`, so those jobs were retried until they dead-lettered. It now delivers the Notification through `attemptSend`, which re-checks consent and skips a Notification already sent, so a replayed job cannot send twice. The job payload now carries the disclosure to re-check; a job without it fails closed. - **Cross-origin support (SUAS-specs D-038, released in 0.7.0).** New `SUAS_CORS_ALLOWED_ORIGINS` (comma-separated exact origins; empty means off). Allowlisted origins get `Access-Control-Allow-Origin` (exact origin, never `*`), `Vary: Origin`, exposed `x-request-id` / `retry-after` / `location`, and preflight answers (`204`) on every endpoint; `Access-Control-Allow-Credentials: true` is sent for `/app` only because `/api/v0` is Bearer-only. This replaces `assertSameOriginBrowserWrite` (the `Origin: null` fix above) with one global origin policy. Every browser-originated unsafe request (POST/PUT/PATCH/DELETE) on any path must be same-origin (`Sec-Fetch-Site: same-origin`, including `Origin: null`) or come from an allowlisted origin, otherwise `403 FORBIDDEN` before body parsing, authentication, rate limiting, or email. Requests with no `Origin` or `Sec-Fetch-Site` and no `/app` cookie (curl, Postman, native iOS and Android apps) are unaffected; a cookie-authenticated unsafe request with neither header is `403`. Without `Sec-Fetch-Site`, the same-origin `Origin` fallback compares scheme as well as host. The `/app` session cookie stays `Secure; HttpOnly; SameSite=Strict; Path=/app` while the allowlist is empty and is `SameSite=None` only when it is non-empty. Allowlist entries containing `*` (also percent-encoded `%2a`), a trailing-dot host, or an empty host label fail startup closed, as do loopback names and IP literals in STAGING and PRODUCTION.
